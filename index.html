Two builds worth explaining

01

Automated data validation & monitoring framework

the problemBroken loads were surfacing days later, in a report, in front of the business — by which point nobody could say which run introduced the error.

  • Config-driven validation job in Databricks comparing source and target row counts, checking for duplicate and null primary keys, and flagging column and datatype changes between loads.
  • Delta Lake table history and time travel used to reconcile each run against its previous version, with run status, row counts and error detail written to a central audit table.
  • Databricks alerts and ADF failure notifications wired in so a failure pages someone at run time.

02

GDPR data erasure & PII anonymisation pipeline

the problemErasure requests had to remove personal data across CRM staging and base tables without orphaning foreign keys or breaking the reports built on top of them.

  • ADF pipeline that picks up erasure requests and calls PL/SQL procedures to anonymise personal data across every affected table.
  • PII columns traced using column-level lineage, then replaced with masked substitutes so referential integrity and downstream reporting survive intact.
  • Every processed request logged as compliance evidence, credentials held in Azure Key Vault, runs scheduled through ADF triggers.
